# 記憶と計算の分割（adapter をコンピュータとして設計する）

> 関連: [index](../index.md) · [learnable-trace](learnable-trace.md) · [top-solutions](../research/top-solutions.md)

**ステータス**: 終了後に上位解法から抽出（自陣では未実施）。出典は 1st・3rd・2nd・5th・10th。

## 一言で

推論時にプログラムを実行できない（提出できるのは LoRA adapter だけ）という制約下で、
**探索を「重みに事前計算表として焼き込む部分」と「トレース内で逐次検証する部分」に割る。**

2nd の言い方が的を射ている:

> adapter をコンピュータとして考えるとよい。**Storage** = 学習中に重みが暗記できる事実（bit の signature、cipher の語彙）。
> **Compute** = 各推論ステップは、すでにトレース上に明示されている入力だけを使う。入力と消費するステップの位置的距離は近いほどよい。

## なぜ必要になったか

cryptarithm の素の探索空間は **10!（桁割当）× 24³（演算規則）≒ 5e10**。
生成予算 7,680 トークンでは書き下せない。一方で LLM の重みは大量の表を暗記できる。
**「探索を短い手続きに分解する」ことが、タスクを解くことと同じくらい本質的な問題**になった（1st の記述）。

## 具体例 1: signature catalog（1st、cryptarithm で唯一 40% 超）

1. 1 つの式 `AB op CD = 出力` を、**記号の反復パターン**に正規化する。
   例: `'^-"} = -@@` → 左辺 `AB`、右辺 `CD`、答えが符号付き `EE` → signature `ABCD-EE`。
2. **被演算子 00..99 × 00..99 × 22 種の非 join 規則を全列挙**し、出力を計算して signature 化。
   → **4,205 個の固有 signature**。各 signature に (演算規則, 桁列, 候補数) の行が付く。
3. この表を**トレースに繰り返し登場させて SFT で暗記させる**。
4. 推論時: DFS の最も高価な部分＝**最初の式**（4〜8 個の記号と規則を一度に決める）を、
   ゼロから探索する代わりに**表から引いた候補で置き換える**。2 番目以降の式は既に固定された桁が使えるので、
   新規に決める記号は 0〜3 個で済み、整合性検査だけで進む。
5. 候補数そのものも暗記対象。**候補数が最小の式を anchor（探索の起点）に選ぶ**ために使う。

> **アイデアの元は他人の議論**（@youkinasa の signature × 事前計算テーブル案）。
> 1st の追加はそれを「推論時のプログラム」ではなく「**SFT で暗記させるカタログ**」に変えたこと。

## 具体例 2: rule-sequence catalog と repair（1st、bit manipulation）

- 8 ビット変換として理論上ありえる規則をすべて列挙し、各々を「出力ビット 0..7 の規則列」に正規化 → 重複除去して **5,238 列**。
- 公開 baseline のソルバはビットごとに規則を選ぶので、**8 個並べると 1 つの整合した変換にならない**ことがある
  （`default 1` のような穴埋めが混ざる）。
- そこで **ハミング距離で最近傍のカタログ列に射影し直す（repair）**。トレースには
  距離の近い候補を最大 32 本だけ列挙して、上から例に照合し、最初に全ビット一致した列を採用する。
  - 32 は理論値ではなく**トークン予算と学習信号の密度から決めた実用値**。
    少なすぎると近い妥当列が入らない。多すぎるとトレースが伸び、候補検査の学習信号が薄くなる。
- 効果: repair 前 public 0.89 → repair + 追加学習で **public 0.91 / private 0.920**。

## 具体例 3: 暗記を先に切り出す二段学習（3rd）

「記憶」と「実行」を同じ 1 回の学習で覚えさせるのは非効率、という判断。

- **第 1 段**: 実タスクを一切含まず、`<RECALL_DOMAINS>` / `<RECALL_ROWS>` タグのドリルだけで学習する。
  「signature を与えたら候補桁集合／候補行を出力する」タスク。1 サンプルに 16 リクエストを packing して収束を速める。
  タグと signature 部分は**損失計算からマスク**（答えだけ学ばせる）。
  → 1,000 signature の検証で overall exact **97.1%**。
- **第 2 段**: その LoRA を初期値として実タスクのトレースで学習。ドリルを 3K だけ混ぜて記憶を保持。
- 効果（同一データ mix での ablation）: **直接学習 12/17 solved・private 0.888 → 二段学習 16/17 solved・private 0.900。**
  12K サンプルの小規模比較では 0/11 → 7/11。
- 副産物: **ソルバのロジックやトレース形式を変えても第 1 段は再利用できる**（モジュール性）。

## 具体例 4: 「継続」の暗記（5th）

@huikang 方式は「1 ビットずつ stride を繋ぐ」ように教える。5th はその逆で、
**8 ビット分の primitive の並び（continuation）約 140 種・固有列約 7,500 を暗記させ、一手で正しいバイト単位変換を構成させた。**
狙いは「ビット単位では例に合うが、バイト単位変換としては存在しない規則」を作らせないこと。

## 効かない条件・反証

- **記憶させる表は「例から検証できる形」で使うこと。** 表を引いて即答させるのではなく、
  引いた候補を例に照合するステップをトレースに残す。1st も「カタログを全展開せず、近傍だけ検査する」形にしている。
- **表が大きすぎると暗記が崩れる。** 3rd は乗算族に限定して 3,678 signature / 11,334 三つ組に抑えた
  （「乗算族は加算・減算より多くの記号を制約するから」）。
- **正解を使って規則を決めた教師トレースは危険。** 18th は expv004/expv006 で
  「gold は *例と整合する候補が複数あるときのタイブレークにだけ* 使う。gold から新しい規則を作らない」という線を引いた。
  それを越えると（697491 のように）解答率が跳ね上がった "良いデータ" ができ、LB は下がる。
- **LoRA の重み側で足し合わせるのは当てにならない。** 10th は SVD merge も seed soup も単体最良に勝てなかった
  （「出力レベルで相補的でも、重みの平均は中間の振る舞いになる」）。18th は SVD 射影 fusion で選択提出にしたが、
  その提出は private では単体最良（expv006 0.880）に負けている。5th の LoRA soup は
  スコアの**安定性**（振れ幅 <1%）には効いたが、CoT 改良と同時に入れたため寄与は切り分けられていない。

## このコンペを離れた形での持ち帰り

**推論時に外部計算を許されないタスク**（オフラインカーネル、ツールなしの LLM 提出、レイテンシ制約）では、
「何を重みに焼き込み、何を出力トークン上で計算させるか」という**予算配分問題**として設計できる。

- 事前計算表 → 重み（Storage）。
- 表の候補を絞る手続きと検証 → トレース（Compute）。
- 表を引く行為自体を、独立した学習タスクとして先に習得させられる（3rd の二段学習）。
