# 可学習トレース（learnable trace）

> 関連: [index](../index.md) · [top-solutions](../research/top-solutions.md) · [memorize-vs-compute](memorize-vs-compute.md) · [postmortem](../postmortem.md)

**ステータス**: 終了後に上位解法から抽出（自陣では未実施）。出典は 4th（原則の明文化）・18th・9th・2nd・10th・discussion 697491。

## 一言で

**「ソルバが正しく解ける」と「LLM がそのトレースを模倣できる」は別の性質。**
CoT トレースは *解いた記録* ではなく *学習可能な軌跡* として設計する。

## なぜ効くか（この形式の前提）

SFT は次トークン予測でしかない。トレースの各行は、**1 回の forward pass で、直前の文脈から導ける**必要がある。
ソルバが内部で行った計算（join、フィルタ、best-of-N の選択）の**結果だけ**を印字すると、
モデルはそこを「文脈から導出できない値」として、統計的な当て推量で埋めることを学ぶ。
これが「隠れ計算（hidden compute）」で、正しいデータでも精度が上がらない主因になる。

discussion 697491 の実測がこれを裏づけている: 合成データの解答率を 87.7% → 95.8% に上げたのに LB は下がった。
base model の logprob で測ると、書き直した cryptarithm_deduce のトレースだけ**明確に確率が低い＝モデルにとって追いにくい**軌跡だった。

## 設計原則（4th place の明文化 + 他チームの実測）

| 原則 | 内容 | 破ったときに起きること |
|---|---|---|
| **隠れ計算の禁止** | 出力する全トークンは、可視の文脈＋小さな固定規則集合から導けること | 「先に決めて後で飾る」を学習する |
| **局所性** | 計算はオペランドの近くに置く。**各行は約 10〜20 行上から計算できる**か、名前付き行の逐語コピーであること | 数千トークン前の値を使う計算は確実に失敗（小さいモデルでは特に） |
| **因果整合** | トレースの *形* は、すでに書かれたものだけに依存してよい | 勝者だけに検証ブロックが付くと「決め打ち → 装飾」を学ぶ |
| **参照整合性** | 導出行が引用できるのは、トレース内に**字面として先に出ている**名前・値だけ | 存在しない参照を捏造する |
| **規則は少なく一様に** | 規則が 1 つ増えるごとに adapter が覚える対象が増える。**数 % のトレースにしか出ない構造は学習されない** | 大量のサンプルが必要になる／全く学ばない |

**この 5 つは機械的に検査できる**という点が重要。4th place は形式を変えるたびに全トレースへ
(a) 参照整合性監査（引用が元ブロックに存在するか）、(b) 局所性監査（導出行が必要とする最遠の参照までのトークン距離を種類別に集計）
をテストとして回した。

## 計測（トレースの良さを、提出せずに測る）

| 指標 | 定義 | 出典・目安 |
|---|---|---|
| **first token divergence** | 学習中に greedy で次トークンを正解トレースと比較。全サンプルが一意なら**未見トレースの eval に相当** | 4th: 一致率 80% ≒ 生成一致 95%（誤りの多くは結果を変えない） |
| **perfect trace rate** | 生成トレースが期待トレースと完全一致する率 | 3rd: bit >85%、cipher・numeric >95% を維持。「答えは合っているがトレースは誤り」の先行検知 |
| **オラクル精度 vs モデル精度の差** | ソルバ自体の解答率と、SFT 済みモデルの解答率の差 | 「ソルバが悪い」と「模倣が失敗している」を分離。1st: 93.16% vs 92.00%、2nd: 99.06% vs 97.32% |
| **base model の logprob** | 書いたトレースの負の対数尤度をカテゴリ別に測る | 低 logprob（追いやすい）ほど学習しやすい。697491 の診断に使われた |
| **ソースが正しいのに予測が誤りの件数** | 教師トレースは正解、モデル出力は誤りのケースを別集計 | 9th: bit 8 件・cipher 2 件など。ここが多いなら形式の問題 |

## トークン予算という制約（このコンペ固有だが構造は一般的）

生成上限 7,680 トークン。**Nemotron のトークナイザは数字・ビット文字をほぼ 1 文字 1 トークンで扱う**ため、
長い 2 進文字列がそのままコストになる。上位が使った圧縮:

- **HEX 化**: 1st は 4 文字以上のビット列を HEX に。生成トークン中央値 **6,771 → 4,888（-27.8%）**。
  3rd は「末尾ビットだけ 2 進で残す HEX」で約 -25%（末尾 2 ビットも HEX にすると 9〜10 例のとき悪化した）。
  6th は計算自体を HEX で行わせ、先頭に HEX 乗算表のチートシートを印字。
- 対称演算子（AND/OR/XOR/XORNOT）は 8C2=28 通りだけ試す（非対称は 56 通り）。2nd。
- **列挙の削除**: 10th は候補リストの `List:` 印字を消した。「長いトレースの最大要因で、暴走生成の原因にもなっていた」。
- 空状態の表記を短くする（`absent` → `none`）。9th。
- 早期終了: 最初に全ビット一致した候補で打ち切る。

**削って浮いたトークンを、より広い規則クラスの検証に回す**のが共通パターン（1st: majority/3入力を追加、3rd: MAJ 探索を追加）。

## 書式の細部で効いたもの（実測ベース）

- **数値の書式は論理より不安定要因になる。** 10 進分解でゼロ位が消えると数値ごとにトレースの見た目が変わる。
  ゼロ位を明示し、**上位桁から先に展開**する順に変えると安定（9th、gravity / unit conversion がほぼ満点に）。
- **文字単位に割る必要がある場面はある。** cipher でモデルが暗号語を写し間違える（文字の抜け・重複）のは、
  人工的な文字列のトークン分割が予測しにくいため。文字分解して対応を明示すると解消（9th）。
- **語彙の裾のトークンを使うなら lm_head / output_layer を学習対象に入れる**（2nd）。
  2nd は非 ASCII の区切り `│` をパース補助に使い、823 問中 5〜10 問の改善を得ている。
- 出力形式そのものを変えて回避した例: cryptarithm の答えに `}` が出ると `\boxed{}` が壊れるので、
  **全カテゴリで `The final answer is: <answer>` 形式に統一**（2nd）。

## 効かない条件・反証

- **短い CoT（結論＋簡単な証明だけ）は失敗する。** 5th は 25 万例で試して LB が崩壊。
  「論理の足場がない状態で LLM は推測できない」。
- **アルゴリズムを賢くすると可学習性が落ちるトレードオフがある。** 1st の cryptarithm ソルバは
  単式候補生成に法演算・不等式のフィルタを入れたが「短いトレースに詰めるのが難しく、それ単体では大きな改善にならなかった」。
- **失敗トレースを除外すると悪化した**（10th）。解けなかった問題のフォールバック・トレースにも学習信号がある。
  9th も「未解決の cryptarithm 形式トレースを混ぜて出力スタイルの一貫性を保った」。
- 難カテゴリの oversample は **3x 程度が上限**。14x で基礎カテゴリの知識を上書きして LB 0.73（697491）。
  9th は bit 5x / cipher 2x / equation 2x、10th は priority 2x（3x で過学習）。

## ここから出たアイデア（次コンペ向け）

- **「モデルに何かを模倣させる」タスクなら、ターゲット側に監査テストを書く。**
  正解率だけでなく、参照整合性・局所性を CI 的に検査する。ターゲット生成器はコードなので検査可能。
- **提出せずに測れる指標を最初に作る**（first token divergence / perfect trace rate）。
  1 提出のノイズが 0.01 ある LB では、これがないと介入の判定ができない。
- **可読性は性能のためのコスト**ではなく、**誤りの切り分けを可能にする投資**（9th の "human-auditable" 主張）。
